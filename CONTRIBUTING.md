# Как внести изменения в руководство

Руководство меняется так же, как код: через ветку, Pull Request, автоматические проверки и ревью. Прямые коммиты в `main` не делаем.

## Как предложить изменение

1. Обновите локальную ветку `main`: `git switch main && git pull`.
2. Создайте ветку от `main`. Имя ветки — тип изменения и короткое описание латиницей через дефис: `docs/accessibility`, `fix/glossary-terms`, `ci/link-check`.
3. Внесите изменения и запустите проверки (см. раздел «Локальная сборка»).
4. Сделайте коммит по правилам ниже и отправьте ветку: `git push -u origin <ветка>`.
5. Откройте Pull Request в `main`. Заполните шаблон описания: что изменено, какие правила затронуты, есть ли отступления.
6. Отправьте ссылку на Pull Request ревьюеру.

Если вы нашли проблему, но не готовы ее исправить, создайте Issue с описанием и примером текста.

## Требования к коммитам

Сообщение коммита пишем по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание>

<тело: зачем нужно изменение, если это не очевидно из описания>
```

**Тип** — что за изменение:

| Тип | Когда использовать |
| --- | --- |
| `docs` | Новое правило, раздел, пример или правка текста |
| `fix` | Исправление ошибки в правиле, ссылке или примере |
| `ci` | Изменение workflow GitHub Actions |
| `build` | Зависимости, настройки MkDocs и линтеров |
| `chore` | Служебные изменения, которые не влияют на сайт |

**Область** — раздел руководства: `voice`, `spelling`, `formatting`, `markdown`, `api`, `glossary`, `templates`, `examples`, `accessibility`, `stylecheck`. Если изменение затрагивает несколько разделов, область не указываем.

**Описание** — на русском языке, со строчной буквы, без точки в конце, до 72 символов. Описание отвечает на вопрос «что сделать»: «добавить правило о диапазонах времени», а не «добавил правило» или «правки».

Если изменение отменяет или меняет смысл существующего правила, после области ставим `!`, а в теле объясняем, что должны поменять авторы.

```text
docs(api): добавить правило о повторе запроса
fix(glossary): исправить определение термина «интервал»
docs(spelling)!: заменить правило о букве «ё»
ci: добавить проверку внешних ссылок
```

## Процесс ревью

1. Pull Request проверяет CI: `markdownlint`, `stylecheck` и `mkdocs build --strict`. Пока проверки не прошли, ревью не начинаем.
2. Ревьюер — не автор изменения. Он проверяет, что правило понятно, не противоречит другим правилам и само написано по руководству.
3. В комментарии ревьюер указывает тип замечания и, если возможно, правило:
    - **Замечание** — нарушено правило, без исправления merge невозможен: «Замечание, ORF-03: здесь нужно тире».
    - **Предложение** — можно сделать лучше, автор решает сам.
    - **Вопрос** — ревьюеру что-то непонятно.
4. Автор отвечает на каждый комментарий. Исправления вносит новым коммитом в ту же ветку, историю во время ревью не переписывает.
5. Обсуждение закрывает тот, кто его открыл, когда ответ его устраивает.
6. После одобрения ревьюера и зеленых проверок автор делает merge в `main`. После merge CI публикует сайт, автор проверяет, что изменения появились на сайте.

## Локальная сборка

Нужны Python 3.12 или новее и Node.js 22 или новее.

```bash
# один раз: окружение и зависимости
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm ci

# проверки перед коммитом
npm run lint
mkdocs build --strict

# просмотр сайта с автообновлением: http://127.0.0.1:8000
mkdocs serve
```

`npm run lint` запускает две проверки: `npm run lint:md` (разметка Markdown) и `npm run lint:style` (правила стиля). Каждую можно запустить отдельно. `stylecheck` можно запустить и для одного файла: `python3 scripts/stylecheck.py docs/rules/voice.md`.

## Как добавить новый раздел

1. Создайте файл в `docs/rules/`. Имя — латиницей через дефис, по правилу MD-01: `docs/rules/accessibility.md`.
2. Первая строка — заголовок раздела, вторая — одно предложение о том, что регулирует раздел, и префикс правил.
3. Выберите префикс из 2–3 латинских букв, который еще не занят. Занятые префиксы перечислены в таблице на главной странице `docs/index.md`.
4. Оформите каждое правило так:

    ```markdown
    ## ACC-01. Название правила {#acc-01}

    **Обязательно.** Текст правила.
    ```

5. Добавьте раздел в навигацию в `mkdocs.yml`, в группу «Правила».
6. Добавьте строку о разделе в таблицу на главной странице `docs/index.md`.
7. Если в разделе появились новые термины, добавьте их в `docs/glossary.md`. Если появились новые нежелательные слова — в `scripts/stop_words.txt`.
8. Запустите проверки и откройте Pull Request по шагам из раздела «Как предложить изменение».
