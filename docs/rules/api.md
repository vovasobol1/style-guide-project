# Описание API

Раздел описывает справочник REST API КампусБук. Префикс правил — `API`. Основной читатель — разработчик интеграции, который знает HTTP и JSON, но не знает устройства сервиса.

## API-01. Описываем метод по шаблону {#api-01}

**Обязательно.** Страница метода содержит разделы в таком порядке:

1. Назначение: одно-два предложения о том, что делает метод и кому он доступен.
2. Запрос: метод HTTP, путь, заголовки, параметры, тело.
3. Ответ: статус успешного ответа и поля тела.
4. Ошибки: таблица кодов.
5. Пример запроса и ответа.

Заготовка — в [шаблоне справочника метода](../doc-templates/api-method.md).

## API-02. Называем страницу действием {#api-02}

**Обязательно.** Заголовок страницы — действие в неопределенной форме: «Создать бронирование», «Получить список аудиторий». Сразу под заголовком указываем метод и путь в блоке кода: `POST /v1/bookings`.

## API-03. Описываем параметры таблицей {#api-03}

**Обязательно.** Параметры пути, запроса и поля тела описываем в таблице со столбцами «Поле», «Тип», «Обязательное», «Описание».

- Тип пишем как в JSON Schema: `string`, `integer`, `boolean`, `array`, `object`. Для даты и времени — `string (date-time)`.
- В столбце «Обязательное» пишем «Да» или «Нет».
- В описании указываем ограничения: допустимые значения, длину, диапазон, значение по умолчанию.
- Если поле может быть `null`, пишем об этом явно и объясняем, что значит `null`.

## API-04. Даем рабочие примеры {#api-04}

**Обязательно.** Пример запроса — команда `curl`, которую можно выполнить после замены токена. Пример ответа — JSON, который действительно возвращает сервис для этого запроса.

- Адрес сервера в примерах — `https://api.campusbook.example`. Домен `.example` зарезервирован для документации и никуда не ведет.
- Токен не пишем в тексте команды, а берем из переменной окружения: `$CAMPUSBOOK_TOKEN`.
- Данные в примерах вымышленные. Не используем настоящие ФИО, номера ИСУ, адреса почты и телефоны.

## API-05. Описываем ошибки с решением {#api-05}

**Обязательно.** Ошибки метода описываем таблицей со столбцами «Статус», «Код», «Причина», «Что сделать». Код — значение поля `code` в теле ответа. В столбце «Что сделать» пишем действие разработчика, а не пересказ причины.

Формат тела ошибки описан один раз на странице «Ошибки» портала API. На странице метода на него ставим ссылку.

## API-06. Записываем дату и время по ISO 8601 {#api-06}

**Обязательно.** В запросах, ответах и примерах дату и время пишем по ISO 8601 с часовым поясом: `2026-10-20T10:00:00+03:00`. В тексте описания используем формат из правила [ORF-07](spelling.md#orf-07).

## API-07. Не переводим имена полей {#api-07}

**Обязательно.** Имена полей, параметров и значений пишем так же, как в API, моноширинным шрифтом. Не переводим, не склоняем и не меняем регистр.

<!-- stylecheck: off -->

| Неправильно | Правильно |
| --- | --- |
| Передайте идентификатор комнаты в поле Room ID. | Передайте идентификатор аудитории в поле `room_id`. |
| Статус меняется на «подтверждено». | Поле `status` принимает значение `confirmed`. |

<!-- stylecheck: on -->

## API-08. Предупреждаем о последствиях повторного запроса {#api-08}

**Обязательно.** Если повтор запроса может создать дубликат или списать лимит, пишем об этом в описании метода и объясняем, как повторить запрос безопасно.
